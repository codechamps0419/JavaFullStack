Kubernetes (Java Backend Developer QA)

Comprehensive Interview Questions & Detailed Answers from a Senior Java Developer Perspective

Created by: Dynamic Duo Learners
  1. Kubernetes Architecture & Control Plane (Qs 1-10)

Q1: What is Kubernetes and why do we use it?

Answer: Kubernetes (K8s) is an open-source container orchestration platform that automates container deployment, scaling and management. We use it to achieve High Availability (HA), automated self-healing (restarting failed containers), horizontal auto-scaling, load balancing and zero-downtime rolling updates across distributed cloud environments.

Q2: What are the key differences between Docker Swarm and Kubernetes?

Answer: Docker Swarm is native to Docker, simpler to set up, but offers basic scaling and limited self-healing. Kubernetes is an enterprise-grade ecosystem with advanced features like automated bin-packing, sophisticated storage orchestration, native service mesh integrations, auto-scaling based on custom metrics (KEDA) and granular declarative configuration.

Q3: How does the Kubernetes control plane work? Explain kube-apiserver, etcd, kube-scheduler and kube-controller-manager.

Answer: The control plane is the brain of the cluster:

  • kube-apiserver: The frontend entry point exposing the REST API that processes configuration changes and receives `kubectl` commands.
  • etcd: A consistent, highly available key-value store acting as the single source of truth for cluster state.
  • kube-scheduler: Watches for newly created pods with no assigned node and selects the optimal worker node based on resource requirements and constraints.
  • kube-controller-manager: Runs background control loops (Node Controller, Job Controller, EndpointSlice Controller) to reconcile actual state toward desired state.

Q4: How does the kubelet work on worker nodes?

Answer: The `kubelet` is the primary node agent running on every worker node. It communicates with the control plane, ensures containers described in PodSpecs are running and healthy, manages local container runtimes (containerd/CRI-O) and reports node/pod health back to the API server.

Q5: What is the role of kubectl?

Answer: `kubectl` is the command-line utility used by developers and operators to interact with the Kubernetes API server. It translates YAML/JSON manifests or imperative commands into REST API requests sent to the control plane.

Q6: What is a Namespace in Kubernetes?

Answer: Namespaces provide logical isolation within a single physical Kubernetes cluster. They allow multi-tenant teams to share cluster resources while isolating deployments, services and RBAC policies (e.g., `default`, `kube-system`, `production`, `staging`).

Q7: What are Taints and Tolerations? How are they different from Node Affinity?

Answer:

  • Taints and Tolerations: Allow a node to repel a set of pods. A taint is applied to a node so it refuses pod placement unless the pod explicitly has a matching toleration (e.g., dedicating GPU nodes to AI/ML workloads).
  • Node Affinity: Attracts pods to a specific set of nodes based on node labels (soft or hard preference), rather than repelling workloads.

Q8: What happens when a Node runs out of memory?

Answer: When a node experiences memory pressure, the Linux kernel triggers the Out-Of-Memory (OOM) killer. Kubernetes detects node pressure via the kubelet and initiates **Node-Eviction**, terminating pods based on their Quality of Service (QoS) class—BestEffort pods are evicted first, followed by Burstable and finally Guaranteed pods.

Q9: How would you investigate a Node-related application failure?

Answer: Run `kubectl describe node <node-name>` to check node conditions (MemoryPressure, DiskPressure, PIDPressure), inspect kernel logs (`dmesg` or `/var/log/messages`), check node resource allocation versus limits and review Kubelet logs via `journalctl -u kubelet`.

Q10: What is Zero Trust Security in Kubernetes?

Answer: Zero Trust dictates that no pod or user is trusted by default, regardless of network location. In Kubernetes, this is achieved through NetworkPolicies (restricting pod-to-pod ingress/egress traffic), mTLS encryption via a Service Mesh (Istio), RBAC least-privilege permissions and immutable container runtimes.

  2. Workloads & Controllers (Qs 11-18)

Q11: What is a Pod in Kubernetes?

Answer: A Pod is the smallest deployable computing unit in Kubernetes. It encapsulates one or more tightly coupled containers sharing storage (volumes), network IP address and IPC namespaces.

Q12: Can a Pod contain multiple containers? Why/when would you use this?

Answer: Yes. We use multi-container pods for helper patterns such as the **Sidecar pattern** (e.g., an Envoy proxy container alongside a Spring Boot app or a log-shipping agent like FluentBit streaming container logs) where containers need to share `localhost` networking and shared storage volumes.

Q13: What is the difference between a Deployment, ReplicaSet and StatefulSet?

Answer:

  • ReplicaSet: Ensures a specified number of identical pod replicas are running (rarely managed directly).
  • Deployment: Manages stateless applications using ReplicaSets underneath, providing declarative rolling updates and rollbacks.
  • StatefulSet: Manages stateful applications (e.g., databases, Kafka) where pods require stable, unique network identifiers (e.g., `kafka-0`, `kafka-1`) and persistent storage mapped ordinality.

Q14: What is the difference between a DaemonSet and Deployment?

Answer: A Deployment runs a specified number of replicas distributed across the cluster nodes arbitrarily. A DaemonSet ensures that *all* (or selected) worker nodes run exactly one copy of a pod, commonly used for node-level agents like log collectors (Fluentbit) or cluster storage daemons.

Q15: How do you perform rolling updates and rollbacks in Kubernetes?

Answer: A rolling update replaces old pods with new ones incrementally based on `maxSurge` and `maxUnavailable` settings. Rollbacks are executed instantly using `kubectl rollout undo deployment/<name>` if a deployment introduces breaking bugs.

Q16: What happens when a Pod crashes?

Answer: The kubelet detects the container termination code. Based on the pod's `restartPolicy` (Always, OnFailure, Never), the kubelet or ReplicaSet controller restarts the container locally or reschedules a replacement pod on a healthy worker node.

Q17: What would you check if a Pod is stuck in Pending state?

Answer: Run `kubectl describe pod <pod-name>` and inspect the `Events` section. Common causes include insufficient CPU/Memory resources on worker nodes, unbound PersistentVolumeClaims (PVC), node selector mismatches or unsatisfied taints and tolerations.

Q18: What happens during a rolling deployment?

Answer: Kubernetes spins up new pods with the updated image version and waits for their Readiness probes to pass. Simultaneously, it terminates old pods gracefully. This ensures zero downtime if readiness probes and graceful shutdown are configured properly.

  3. Configuration & Secrets (Qs 19-24)

Q19: What is the difference between ConfigMap and Secret?

Answer: Both store key-value pairs for applications. ConfigMaps store plain-text configuration properties. Secrets store base64-encoded sensitive data (passwords, tokens, certificates). *Note:* Base64 encoding is not encryption; production clusters should enable etcd encryption at rest and use tools like HashiCorp Vault.

Q20: How do you secure secrets in Kubernetes?

Answer: Standard K8s secrets are stored unencrypted in `etcd`. To secure them: (1) Enable etcd encryption-at-rest, (2) Restrict RBAC access to secrets namespaces, (3) Use external secret managers like HashiCorp Vault, AWS Secrets Manager or External Secrets Operator to inject secrets directly into memory without persisting them in cluster YAML.

Q21: How do you inject ConfigMaps and Secrets into Spring Boot without restarting the application?

Answer: Mount the ConfigMap as a volume inside the pod container rather than as environment variables. When Kubernetes updates a volume-mounted ConfigMap, the file updates on disk. Using Spring Cloud Kubernetes or `@RefreshScope` enables dynamic property reloads.

Q22: How do you migrate away from Spring Cloud Config Server to native Kubernetes configuration patterns?

Answer: Convert property files from the central git repository into Kubernetes `ConfigMaps`. Bind the ConfigMaps into your Deployment manifest using `envFrom` or volume mounts and remove the `spring-cloud-config-client` dependency from your Spring Boot project.

Q23: How does dynamic secret rotation (Vault) work with Spring Boot DB connection pools (HikariCP)?

Answer: When database credentials rotate in Vault, HikariCP maintains open connections with old credentials. To handle this without crashing the pod, listen to property change events, invoke `HikariDataSource.setPassword(newPassword)` and call `dataSource.getHikariPoolMXBean().softEvictConnections()` to gracefully refresh connections.

Q24: How do you manage multi-environment `application.yml` profiles when deploying via Helm or Kustomize?

Answer: Keep your Spring Boot JAR file configuration generic. Use Helm `values-dev.yaml`, `values-prod.yaml` or Kustomize overlays to inject environment-specific properties into Kubernetes ConfigMaps, which are mounted into the application pod at runtime.

  4. Networking & Service Discovery (Qs 25-34)

Q25: What are Kubernetes Services? Name the different types.

Answer: A Kubernetes Service is an abstraction layer that defines a logical set of Pods and a policy to access them. Types include:

  • ClusterIP: Exposes the service on an internal cluster IP (default).
  • NodePort: Exposes the service on a static port on each node's IP.
  • LoadBalancer: Provisions an external cloud load balancer pointing to the NodePort.
  • ExternalName: Maps a service to a DNS name.

Q26: How do you expose a Pod to the outside world?

Answer: By creating a `LoadBalancer` or `NodePort` Service or by routing external traffic through an **Ingress Controller** (e.g., NGINX Ingress) coupled with an Ingress resource managing HTTP/HTTPS routing rules, path-based routing and SSL termination.

Q27: How does Kubernetes Service Discovery work?

Answer: Kubernetes provides built-in service discovery via internal cluster DNS (CoreDNS) and environment variables. When a service is created, CoreDNS registers an A record (`my-service.namespace.svc.cluster.local`). Pods resolve this name to a ClusterIP or direct endpoint IPs.

Q28: What is a Headless Service (`clusterIP: None`) and when would a Spring Boot app require it?

Answer: A headless service has no ClusterIP assigned. Instead, DNS queries return the individual IP addresses of all pods matching the selector. Spring Boot microservices require this when performing direct peer-to-peer discovery (e.g., embedded Hazelcast clusters or specialized Kafka consumers without API Gateways).

Q29: How would you debug DNS resolution problems between Pods?

Answer: Run an ephemeral debug pod with `kubectl run busybox --image=busybox:1.28 --rm -it -- sh`, test name resolution using `nslookup my-service`, inspect CoreDNS logs (`kubectl logs -n kube-system -l k8s-app=kube-dns`) and check `/etc/resolv.conf` inside the failing pod.

Q30: How would you troubleshoot a Kubernetes Service that is not routing traffic?

Answer: (1) Verify Service selector matches pod labels (`kubectl get endpoints <service-name>`), (2) Check if target container ports match service `targetPort`, (3) Test connectivity directly against pod IPs using `curl`, (4) Inspect network policies blocking traffic.

Q31: What happens if a Service has no healthy endpoints?

Answer: If all backing pods fail their Readiness probes or crash, the Service endpoints list becomes empty. Clients attempting to connect to the Service will receive connection timeouts or HTTP 503 Service Unavailable errors.

Q32: How would you troubleshoot intermittent network failures?

Answer: Check CNI plugin status (Calico/Flannel), investigate MTU mismatch issues across cluster nodes, inspect iptables or eBPF routing rules, check for CPU throttling dropping packets and review ingress controller logs for upstream connection resets.

Q33: How would you investigate slow API responses inside Kubernetes?

Answer: (1) Check if the pod is experiencing CPU throttling due to strict limits, (2) Inspect distributed traces via Micrometer/OpenTelemetry to identify slow database queries or downstream HTTP calls, (3) Verify JVM Garbage Collection pauses via Actuator metrics.

Q34: How would you trace a request across multiple Pods?

Answer: Implement distributed tracing using Micrometer Tracing and OpenTelemetry. Pass W3C trace context headers (`traceparent`, `tracestate`) across HTTP and Kafka messaging boundaries and aggregate traces in Jaeger, Zipkin or Grafana Tempo.

  5. Pod Lifecycle, Probes & JVM Memory Management (Qs 35-44)

Q35: Readiness Probe vs. Liveness Probe?

Answer:

  • Liveness Probe: Determines if the container needs to restart (e.g., JVM deadlock). If it fails, Kubernetes kills the pod.
  • Readiness Probe: Determines if the pod can accept traffic (e.g., database pool connected). If it fails, Kubernetes removes the pod IP from service endpoints without restarting the container.

Q36: What are Readiness and Liveness probes?

Answer: They are health check mechanisms executed by the kubelet against container endpoints (HTTP, TCP or Exec commands) to ensure application health and automated traffic routing control.

Q37: How can an incorrect readiness probe cause production issues?

Answer: If a readiness probe checks a heavy DB query with an aggressive timeout period, transient database load will cause the readiness probe to fail. Kubernetes will instantly pull all pods out of service rotation, causing a total outage even though the JVM is healthy.

Q38: How can an incorrect liveness probe create a restart loop?

Answer: If a liveness probe checks too frequently (`periodSeconds: 2`) or has an insufficient `initialDelaySeconds` before the Spring Boot application finishes context loading and database migrations, the liveness probe will fail repeatedly, putting the container into an infinite `CrashLoopBackOff` restart loop.

Q39: How do startup probes help Java applications?

Answer: Startup probes disable liveness and readiness checks until the application has successfully booted up. This protects slow-starting Spring Boot apps running Flyway migrations from being killed prematurely by strict liveness probes.

Q40: How do you configure Liveness, Readiness and Startup probes for a Spring Boot 3 microservice and why are all three necessary?

Answer: All three are necessary to manage Spring's heavy initialization footprint, prevent premature restarts and dynamically remove unhealthy pods from traffic rotation without killing the JVM.

startupProbe:
  httpGet:
    path: /actuator/health/startup
    port: 8080
  failureThreshold: 30
  periodSeconds: 5
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080

Q41: How do you implement Graceful Shutdown in Spring Boot (`server.shutdown=graceful`) when running inside a Kubernetes Pod?

Answer: Configure `server.shutdown=graceful` and `spring.lifecycle.timeout-per-shutdown-phase=30s` in `application.yml`. When the pod receives `SIGTERM`, Tomcat stops accepting new requests while giving active threads time to finish in-flight requests.

Q42: What does OOMKilled mean?

Answer: It means the container process exceeded its memory limit specified in the Kubernetes manifest. The Linux kernel terminated the container with Exit Code 137.

Q43: How do Kubernetes memory limits affect JVM heap sizing?

Answer: Older JVMs were container-unaware and read host RAM, often causing OOMKilled errors. Modern JDKs use `-XX:+UseContainerSupport` and `-XX:MaxRAMPercentage=75.0` to calculate heap relative to container memory limits, leaving 25% headroom for off-heap memory, Metaspace and thread stacks.

Q44: How would you troubleshoot Java heap issues inside a Kubernetes Pod?

Answer: Check pod exit code 137 (`kubectl describe pod`), capture a heap dump from the live pod using `jcmd <pid> GC.heap_dump /tmp/heap.hprof` and analyze it with Eclipse MAT or VisualVM to detect memory leaks or insufficient container memory allocation.

  6. Observability & Troubleshooting (Qs 45-56)

Q45: How would you troubleshoot a Spring Boot Pod in CrashLoopBackOff?

Answer: Run `kubectl logs <pod-name> --previous` to check application startup stack traces, verify database connection properties in mounted ConfigMaps/Secrets, check if liveness probes are failing too early and review resource limit constraints.

Q46: What causes Pod eviction?

Answer: Node-level resource exhaustion (MemoryPressure, DiskPressure or PIDPressure). When a node runs low on resources, the kubelet forcibly terminates pods to protect node stability.

Q47: How would you troubleshoot a Pod evicted by Kubernetes?

Answer: Run `kubectl describe pod <evicted-pod>` to check eviction reasons (`The node was low on resource: memory`). Adjust container resource requests/limits or scale up worker node instance sizes.

Q48: Why might a Spring Boot application fail immediately after deployment?

Answer: Common causes include missing environment variables or secret keys, database migration failures (Flyway syntax error), port binding conflicts or invalid YAML syntax in mounted ConfigMaps.

Q49: How would you troubleshoot environment variables missing inside a Pod?

Answer: Run `kubectl exec -it <pod-name> -- env` to inspect active environment variables and verify that `envFrom`, `configMapRef` or `secretRef` key references in the deployment manifest are spelled correctly.

Q50: How would you investigate high CPU usage in a Java Pod?

Answer: Capture a thread dump using `jcmd 1 Thread.print`, analyze CPU-heavy threads (e.g., infinite loops, heavy GC thrashing), check Prometheus metrics for Garbage Collection duration and check if CPU limits are causing CPU throttling.

Q51: What happens when a Pod exceeds its CPU limit?

Answer: Unlike memory (which triggers OOMKilled), exceeding CPU limits does *not* kill the container. Instead, the Linux kernel throttles the container's CPU cycles, severely degrading application throughput and increasing latency.

Q52: What is CPU throttling and how can it affect Java applications?

Answer: CPU throttling occurs when CFS (Completely Fair Scheduler) pauses container execution because it consumed its allotted CPU quota within a period window. For Java apps, this pauses JVM threads, distorts metrics and spikes HTTP request response times.

Q53: How would you identify whether a performance issue is caused by Kubernetes or the JVM?

Answer: Check Prometheus metrics for Kubernetes CPU throttling (`container_cpu_cfs_throttled_periods_total`) versus JVM Garbage Collection pause times (`jvm.gc.pause`). High throttling points to K8s limits; high GC pauses point to JVM heap tuning.

Q54: How would you troubleshoot a failed health check?

Answer: Check Spring Boot Actuator health endpoint directly via `kubectl exec <pod> -- curl localhost:8080/actuator/health`, review actuator component details for database or disk failures and check kubelet event logs.

Q55: How would you debug a Java application that works locally but fails in Kubernetes?

Answer: This is typically caused by environment differences (database URLs, missing environment variables, stricter memory limits triggering container OOM or DNS resolution issues). Inspect pod logs, use ephemeral debug containers and verify configuration parity.

Q56: How would you investigate a sudden increase in Pod latency after deployment?

Answer: Compare new vs old container resource limits (CPU throttling), review distributed traces to find slow downstream SQL queries or external REST calls introduced in the release and check database connection pool exhaustion.

  7. Auto-scaling, Storage & Advanced Architecture (Qs 57-68)

Q57: HPA vs VPA?

Answer:

  • HPA (Horizontal Pod Autoscaler): Scales pod replica count up or down based on CPU, memory or custom metrics. Ideal for stateless Spring Boot apps.
  • VPA (Vertical Pod Autoscaler): Adjusts CPU and memory limits/requests for existing pods (often requires pod restarts).

Q58: How does HPA work with Spring Boot applications?

Answer: HPA queries the Metrics Server periodically. When average CPU or custom metric utilization exceeds target thresholds (e.g., 70%), HPA updates the Deployment replica count to handle incoming traffic loads.

Q59: Why might HPA fail to scale a Java application?

Answer: (1) Metrics Server is not installed or running, (2) Container resource requests (`resources.requests`) are not defined in the deployment manifest, preventing HPA from calculating percentage usage or (3) JVM warmup spikes CPU immediately, causing premature scaling storms.

Q60: CPU-based vs custom-metric-based autoscaling?

Answer: CPU-based scaling reacts to compute load but can lag behind traffic surges (e.g., event-driven Kafka consumers where CPU is low while queue lag is massive). Custom-metric scaling (via KEDA or Prometheus Adapter) scales based on application-specific metrics like Kafka consumer lag or active HTTP requests.

Q61: How would you scale a Java application in Kubernetes?

Answer: Ensure the Spring Boot application is completely stateless (externalizing session state to Redis, file uploads to S3), configure container resource requests/limits and attach an HPA or KEDA ScaledObject for automated horizontal scaling.

Q62: What are Persistent Volumes (PV) and Persistent Volume Claims (PVC)?

Answer:

  • Persistent Volume (PV): A cluster-wide piece of storage provisioned by an administrator or dynamically via StorageClasses.
  • Persistent Volume Claim (PVC): A request for storage by a user/pod specifying size and access modes (e.g., ReadWriteOnce). Pods mount PVCs to persist data beyond container lifecycle restarts.

Q63: How do you collect logs, metrics and traces during a production incident?

Answer: Use the unified Observability stack: Logs via Fluentbit/Loki, Metrics via Prometheus/Grafana dashboards and Distributed Traces via Micrometer OpenTelemetry and Jaeger.

Q64: How would you troubleshoot a Java microservice that becomes slow only under heavy traffic?

Answer: Check HikariCP connection pool exhaustion (threads waiting for DB connections), inspect GC pause durations under heavy heap allocation, check Tomcat thread pool saturation and evaluate K8s CPU throttling limits.

Q65: A Spring Boot service is experiencing high CPU, frequent restarts and increasing latency. How would you investigate the issue end-to-end?

Answer: (1) Run `kubectl describe pod` to check exit codes (OOMKilled 137 or probe failures), (2) Check pod logs for OutOfMemoryError or deadlock exceptions, (3) Analyze thread dumps for blocked threads, (4) Verify if liveness probes are misconfigured and killing healthy pods under load.

Q66: How do you handle Database Per Microservice migrations (Flyway / Liquibase) during rolling deployments on Kubernetes?

Answer: Avoid running DB migrations directly inside multiple starting pod replicas simultaneously to prevent race conditions. Instead, execute migrations using Kubernetes **InitContainers** or Kubernetes Job resources prior to deploying the main application container.

Q67: How do Java 21 Virtual Threads (Project Loom) impact thread pool sizing and resource limits in a Kubernetes container?

Answer: Virtual threads decouple application tasks from OS threads. In a K8s container, this allows Spring Boot apps to handle tens of thousands of concurrent requests with minimal CPU overhead, shifting resource bottlenecks from OS thread limits to database connection pool limits.

Q68: How do you optimize Spring Boot startup times on Kubernetes using Spring AOT, GraalVM Native Images or CRaC?

Answer: Traditional JVM cold starts take 15-30 seconds. By compiling Spring Boot apps into **GraalVM Native Images** or using **CRaC** (Coordinated Restore at Checkpoint) snapshots, pod startup times drop to under 100 milliseconds, dramatically improving Kubernetes auto-scaling responsiveness.
