Git Command Cheat Sheet

Only practical, currently used Git commands - organized into Basic, Intermediate and Advanced levels with a simple explanation of what each command does and when to use it.

🌟 Created by ~ Dynamic Duo Learners 🤜🤛

Git Areas Diagram

This visual shows where your code lives during day-to-day Git work and which commands move changes from one area to another.

1) Working Directory

This is where you actually edit files in your project. New files, modified files and deleted files first appear here.

2) Staging Area

The staging area is like a preparation zone. You choose exactly what should go into the next commit by using git add. Git internally stores staging information in: .git/index

3) Local Repository

After git commit, changes become part of your local Git history. This is stored on your machine and is not yet shared with the team.

4) Remote Repository

This is the shared server copy of the code. Use git push to send work there and git fetch / git pull to get updates.

5) Stash Area

Use git stash when your work is incomplete but you need to switch branches or pull cleanly. It stores temporary changes outside the normal commit flow.

Useful Mental Model

Working Directory = current files, Staging Area = selected changes, Local Repository = committed history, Remote = team-shared history, Stash = temporary parking area.

Basic Level

🌱 Basic Level Git Commands

Repository setup, daily changes, commits, branches and remote collaboration.

22commands
git --version

What it does: Check the installed Git version.

When to use: Use when verifying Git installation or troubleshooting environment setup.

git config --global user.name "Your Name"

What it does: Set the author name used in commits.

When to use: Run once on your machine or whenever your Git identity changes.

git config --global user.email "you@example.com"

What it does: Set the author email used in commits.

When to use: Use the email connected to your Git hosting account when required.

git clone <repository-url>

What it does: Download an existing remote repository.

When to use: Use when starting work on a project already hosted on GitHub, GitLab, Bitbucket, or another server.

git init

What it does: Create a new Git repository in the current folder.

When to use: Use when starting version control for a new local project.

git status

What it does: Show the current branch and changed, staged, or untracked files.

When to use: Run frequently before adding, committing, switching branches, or resolving conflicts.

git diff

What it does: Show unstaged changes in tracked files.

When to use: Review exactly what changed before staging.

git diff --staged

What it does: Show changes already added to the staging area.

When to use: Review what will be included in the next commit.

git add <file-name>

What it does: Stage one file for the next commit.

When to use: Use when you want a focused commit containing selected files.

git add .

What it does: Stage all changes under the current directory.

When to use: Use after reviewing the changes and confirming they belong in one commit.

git commit -m "feat: add user API"

What it does: Create a commit from staged changes.

When to use: Write a short message describing what the commit changes.

git log --oneline

What it does: Show commit history in a compact format.

When to use: Use for quick history review and finding commit IDs.

git log --oneline --graph --decorate --all

What it does: Display a visual branch and commit graph.

When to use: Useful for understanding merges, branch history and current pointers.

git branch

What it does: List local branches.

When to use: The current branch is marked with an asterisk.

git switch <branch-name>

What it does: Switch to an existing branch.

When to use: Preferred modern command for branch switching.

git switch -c <new-branch-name>

What it does: Create and immediately switch to a new branch.

When to use: Use when beginning a feature, bug fix, or experiment.

git branch -d <branch-name>

What it does: Safely delete a merged local branch.

When to use: Git refuses deletion when unmerged work may be lost.

git remote -v

What it does: Display remote repository names and URLs.

When to use: Use to verify where fetch and push operations are connected.

git fetch origin

What it does: Download remote commits and branch updates without changing your working branch.

When to use: Use before comparing, merging, or rebasing with remote work.

git pull --ff-only

What it does: Update the current branch only when a fast-forward is possible.

When to use: A safe pull option that avoids creating an unexpected merge commit.

git push -u origin <branch-name>

What it does: Push a branch and set its upstream remote.

When to use: Usually used the first time a new branch is pushed.

git push

What it does: Push commits to the configured upstream branch.

When to use: Use after upstream tracking has already been configured.

Intermediate Level

🛠️ Intermediate Level Git Commands

Team workflows, conflict handling, stashing, undo operations and clean feature branches.

25commands
git restore <file-name>

What it does: Discard unstaged changes in one tracked file.

When to use: Use carefully because the local edits are removed.

git restore .

What it does: Discard all unstaged changes in the current directory.

When to use: Use only after confirming those edits are not needed.

git restore --staged <file-name>

What it does: Remove a file from staging while keeping its local changes.

When to use: Useful when a file was added accidentally.

git stash push -m "WIP: payment changes"

What it does: Temporarily save uncommitted work with a label.

When to use: Use before switching branches or pulling updates when work is incomplete.

git stash push -u -m "WIP with new files"

What it does: Stash tracked and untracked files together.

When to use: Use when newly created files must also be saved temporarily.

git stash list

What it does: List all saved stashes.

When to use: Use to find the stash you want to restore.

git stash pop

What it does: Apply the latest stash and remove it from the stash list.

When to use: Use when returning to temporarily saved work.

git stash apply stash@{0}

What it does: Apply a specific stash without deleting it.

When to use: Useful when you want to reuse or verify a saved stash.

git merge <branch-name>

What it does: Combine another branch into the current branch.

When to use: Use when preserving branch history or following a merge-based team workflow.

git merge --abort

What it does: Cancel a conflicted merge and return to the pre-merge state.

When to use: Use when the merge should be restarted or abandoned.

git rebase origin/main

What it does: Replay current branch commits on top of the latest remote main branch.

When to use: Use on a private feature branch to maintain a clean linear history.

git rebase --continue

What it does: Continue a rebase after resolving conflicts.

When to use: Stage the resolved files first with `git add`.

git rebase --abort

What it does: Cancel the current rebase and restore the previous state.

When to use: Use when the rebase becomes unsafe or too complicated.

git commit --amend --no-edit

What it does: Add staged changes to the most recent commit without changing its message.

When to use: Use only when the latest commit has not been shared, or your team permits rewriting it.

git commit --amend -m "fix: correct validation"

What it does: Change the latest commit message.

When to use: This rewrites the latest commit ID.

git revert <commit-id>

What it does: Undo a commit by creating a new reverse commit.

When to use: Preferred for changes already pushed to a shared branch.

git reset --soft HEAD~1

What it does: Remove the latest local commit but keep its changes staged.

When to use: Useful when you need to rebuild or split the last unpushed commit.

git reset HEAD~1

What it does: Remove the latest local commit and keep its changes unstaged.

When to use: Useful when you want to edit and restage the changes.

git cherry-pick <commit-id>

What it does: Apply one specific commit from another branch.

When to use: Use when only a selected fix or change is required.

git show <commit-id>

What it does: Display the metadata and patch for a commit.

When to use: Use during code review, investigation, or debugging.

git blame <file-name>

What it does: Show the latest commit and author for each line.

When to use: Useful for understanding why a line changed; avoid using it to assign blame.

git branch -r

What it does: List remote-tracking branches.

When to use: Use to see branches available on the remote.

git push origin --delete <branch-name>

What it does: Delete a branch from the remote repository.

When to use: Use after merging and confirming the remote branch is no longer needed.

git tag -a v1.0.0 -m "Release 1.0.0"

What it does: Create an annotated release tag.

When to use: Use for meaningful releases because annotated tags store metadata and a message.

git push origin v1.0.0

What it does: Push one tag to the remote repository.

When to use: Use after creating a release tag locally.

Advanced Level

🚀 Advanced Level Git Commands

History cleanup, recovery, debugging, parallel work and repository investigation.

19commands
git rebase -i HEAD~5

What it does: Interactively edit the most recent five commits.

When to use: Use to squash, reorder, reword, or remove private feature-branch commits.

git push --force-with-lease

What it does: Safely update a remote branch after rewriting local history.

When to use: Prefer this over `--force`; it refuses to overwrite unexpected remote changes.

git reflog

What it does: Show recent movements of HEAD and branch references.

When to use: Use to recover commits lost after reset, rebase, or accidental branch changes.

git branch recovery <commit-id>

What it does: Create a recovery branch from a found commit.

When to use: Use after locating the required commit in reflog.

git bisect start

What it does: Begin binary search for the commit that introduced a bug.

When to use: Mark known good and bad commits, then test the commits Git selects.

git bisect good <commit-id>

What it does: Mark a commit as working during bisect.

When to use: Helps Git narrow the search range.

git bisect bad <commit-id>

What it does: Mark a commit as broken during bisect.

When to use: Defines the bad side of the search range.

git bisect reset

What it does: Finish bisect and return to the original branch.

When to use: Run after identifying the problematic commit.

git log -S "searchText" --oneline

What it does: Find commits that changed the number of occurrences of exact text.

When to use: Useful for discovering when a method, flag, or constant was added or removed.

git log -G "regexPattern" --oneline

What it does: Find commits whose patch matches a regular expression.

When to use: Useful for broader code-history investigations.

git log -- <file-name>

What it does: Show the commit history of one file.

When to use: Use when investigating how a specific file evolved.

git diff main...HEAD

What it does: Show changes introduced by the current branch since it diverged from main.

When to use: Useful before opening or reviewing a pull request.

git worktree add ../hotfix hotfix-branch

What it does: Check out another branch in a separate working directory.

When to use: Use to work on an urgent fix without stashing or switching your current work.

git worktree list

What it does: List all linked working directories.

When to use: Use to see which branches are open in worktrees.

git worktree remove ../hotfix

What it does: Remove a linked worktree.

When to use: Run after finishing and cleaning the additional working directory.

git clean -n

What it does: Preview untracked files and folders that would be removed.

When to use: Always run this before an actual clean.

git clean -fd

What it does: Delete untracked files and directories.

When to use: Destructive command; use only after reviewing `git clean -n`.

git reset --hard origin/main

What it does: Make the current local branch exactly match remote main.

When to use: Destructive recovery operation; all uncommitted local changes are removed.

git fsck

What it does: Check the integrity and connectivity of Git objects.

When to use: Useful when diagnosing repository corruption or locating dangling objects.

📌 Most Common Feature-Branch Workflow

A practical workflow for starting, updating, reviewing and pushing feature development.

1

Update the main branch

git switch main
git fetch origin
git pull --ff-only

Start from the latest stable code before creating a feature branch.

2

Create the feature branch

git switch -c feature/user-api

Keep feature work isolated from the main branch.

3

Review and commit changes

git status
git diff
git add .
git commit -m "feat: add user API"

Review changes before creating a focused commit.

4

Update before opening the PR

git fetch origin
git rebase origin/main

Replay private feature commits on the latest main branch and resolve conflicts locally.

5

Push the branch

git push -u origin feature/user-api

Push the branch and configure upstream tracking.

Fetch Vs Pull

Both communicate with a remote repository, but only pull updates the current branch immediately.

git fetch

Meaning: Downloads remote commits and branch references.

Current branch: Not modified.

Best use: Review remote changes before merging or rebasing.

Safer for: Controlled team workflows.

git pull --ff-only

Meaning: Fetches and updates the current branch only when fast-forward is possible.

Current branch: Updated immediately.

Best use: Updating a branch without creating an unexpected merge commit.

Note: It stops when histories have diverged.

Merge Vs Rebase

Both integrate work from another branch, but they produce different histories.

Merge

Command: git merge <branch>

History: Preserves the original branch structure.

May create: A merge commit.

Best for: Shared branches and teams that want full branch history.

Rebase

Command: git rebase origin/main

History: Rewrites feature commits into a linear sequence.

Best for: Private feature branches before a pull request.

Warning: Avoid rebasing commits already used by other developers.

Reset Vs Revert

Choose based on whether the commit has already been shared with others.

Reset

Purpose: Moves the branch pointer to another commit.

Effect: Rewrites local history.

Best for: Local, unpushed commits.

Risk: Hard reset can permanently discard work.

Revert

Purpose: Creates a new commit that reverses an earlier commit.

Effect: Preserves existing history.

Best for: Commits already pushed to a shared branch.

Team-safe: Yes, because it does not remove published commits.

Soft Vs Mixed Vs Hard Reset

All three move the branch pointer, but they handle the staging area and working files differently.

Mode Command Staging Area Working Files Use Case
Soft git reset --soft HEAD~1 Changes remain staged Changes remain Rebuild or combine the latest local commit
Mixed git reset HEAD~1 Changes become unstaged Changes remain Edit and selectively stage the last commit again
Hard git reset --hard HEAD~1 Changes removed Changes removed Discard an unwanted local commit and its changes

Checkout Vs Switch Vs Restore

checkout is still supported, but modern Git provides clearer commands with focused responsibilities.

Command Primary Purpose Recommended Usage
git switch Create or change branches Use for modern branch navigation, such as git switch main or git switch -c feature/name.
git restore Restore file content or unstage files Use for file operations, such as git restore file.txt or git restore --staged file.txt.
git checkout Older multipurpose branch and file command Know it for existing scripts and older repositories, but prefer switch and restore for new daily usage.

🔔 Safe And Risky Commands

Safe commands mainly inspect or preserve history; risky commands can rewrite history or delete work.

🛡️ Generally Safe

  • git status — inspect current state
  • git diff — review changes
  • git log — inspect history
  • git fetch — download remote updates
  • git stash — temporarily preserve work
  • git revert — safely reverse a shared commit

⚠️ Use Carefully

  • git reset --hard — discards local changes
  • git clean -fd — deletes untracked files and folders
  • git rebase — rewrites commit history
  • git commit --amend — changes the latest commit ID
  • git push --force-with-lease — replaces remote branch history
  • git branch -D — force-deletes an unmerged branch

Useful Aliases

Aliases shorten frequently used commands. Keep them readable so team members can understand your workflow.

Short status

Run git st instead of git status.

git config --global alias.st status
Visual history

Displays an easy-to-read commit and branch graph.

git config --global alias.lg "log --oneline --graph --decorate --all"
Short branch listing

Run git br to list branches.

git config --global alias.br branch
Short commit command

Run git ci -m "message" for a commit.

git config --global alias.ci commit

ᯓ➤ Good Commit Message Format

Use a short type followed by a clear description of the change.

<type>: <short description>
Type Purpose Example
feat New functionality feat: add user registration API
fix Bug correction fix: handle null payment response
refactor Code improvement without behavior change refactor: simplify order validation
test Test additions or updates test: add payment service tests
docs Documentation changes docs: update deployment steps
chore Maintenance work chore: update build dependencies
perf Performance improvement perf: reduce product query time
ci CI/CD configuration ci: add pull request build

Good practice: Keep the subject concise, use an action-focused description and create one logical change per commit.

Golden Rules

1. Run git status before important operations.
2. Review git diff before committing.
3. Fetch before merge or rebase.
4. Keep commits small and focused.
5. Write meaningful commit messages.
6. Prefer revert for pushed commits.
7. Prefer force-with-lease after rebase.
8. Do not force-push shared branches.
9. Use destructive commands only after checking their impact.
10. Keep feature branches updated with the target branch.

🚩 Important Team Rules

Private feature branches: Rebase and amend are normally safe before others depend on those commits.

Shared branches: Prefer git revert instead of rewriting published history.

Force push: Use git push --force-with-lease rather than plain --force.

Destructive cleanup: Preview with git clean -n before running git clean -fd.
