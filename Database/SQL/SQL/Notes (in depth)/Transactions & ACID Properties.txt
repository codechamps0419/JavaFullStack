==================================================
1. WHAT IS A TRANSACTION?
==================================================

A Transaction is a group of one or more SQL statements that are executed as a single logical unit of work.

Simple Meaning:

Either all operations succeed,
or all operations fail.

There should be no partial execution.

Example:

Bank Transfer

Step 1:
Deduct 1000 from Account A

Step 2:
Add 1000 to Account B

Both operations must succeed.

If one fails,
entire transaction must fail.

Interview Answer:

A transaction is a sequence of SQL operations executed as a single unit of work that follows ACID properties.

==================================================
2. WHY DO WE NEED TRANSACTIONS?
==================================================

Transactions are needed to:

1. Maintain data consistency
2. Prevent partial updates
3. Ensure reliability
4. Handle failures safely
5. Protect business data
6. Support concurrent users

Real examples:

- Bank transfer
- Order placement
- Payment processing
- Ticket booking
- Inventory updates
- Wallet recharge

==================================================
3. TRANSACTION EXAMPLE
==================================================

ACCOUNT table:

| account_id | balance |
|------------|---------|
| 1          | 5000    |
| 2          | 3000    |

Transfer 1000 from Account 1 to Account 2.

BEGIN;

UPDATE account
SET balance = balance - 1000
WHERE account_id = 1;

UPDATE account
SET balance = balance + 1000
WHERE account_id = 2;

COMMIT;

Result:

Account 1 = 4000
Account 2 = 4000

==================================================
4. WHAT IF FAILURE OCCURS?
==================================================

Suppose:

Step 1 succeeds:

Account 1 = 4000

Step 2 fails:

Money not added to Account 2.

Without transaction:

Money disappears.

This is data corruption.

With transaction:

Database rolls back.

Account 1 returns to 5000.

Account 2 remains 3000.

Data stays correct.

==================================================
5. TRANSACTION STATES
==================================================

Transaction goes through states:

1. Active
2. Partially Committed
3. Committed
4. Failed
5. Aborted

Flow:

Active
   ↓
Partially Committed
   ↓
Committed

OR

Active
   ↓
Failed
   ↓
Aborted (Rollback)

==================================================
7. COMMIT
==================================================

COMMIT permanently saves changes.

Example:

BEGIN;

UPDATE employee
SET salary = 60000
WHERE emp_id = 101;

COMMIT;

After COMMIT:

Changes are permanent.

Interview Answer:

COMMIT makes all transaction changes permanent in the database.

==================================================
8. ROLLBACK
==================================================

ROLLBACK cancels changes made in transaction.

Example:

BEGIN;

UPDATE employee
SET salary = 60000
WHERE emp_id = 101;

ROLLBACK;

Result:

Salary returns to original value.

Interview Answer:

ROLLBACK undoes all uncommitted changes in the current transaction.

==================================================
9. SAVEPOINT
==================================================

Savepoint creates a checkpoint inside transaction.

Example:

BEGIN;

UPDATE account
SET balance = balance - 1000
WHERE account_id = 1;

SAVEPOINT transfer_point;

UPDATE account
SET balance = balance + 1000
WHERE account_id = 2;

ROLLBACK TO transfer_point;

COMMIT;

Only operations after savepoint are rolled back.

Interview Answer:

SAVEPOINT allows partial rollback within a transaction.

==================================================
10. RELEASE SAVEPOINT
==================================================

Removes savepoint.

Syntax:

RELEASE SAVEPOINT savepoint_name;

Example:

RELEASE SAVEPOINT transfer_point;

==================================================

Most Important Interview Topic

ACID stands for:

A → Atomicity
C → Consistency
I → Isolation
D → Durability

Every reliable relational database follows ACID principles.

Interview Answer:

ACID properties ensure reliable, consistent, and safe transaction processing.

==================================================
12. ATOMICITY
==================================================

Atomicity means:

All or Nothing.

Either entire transaction succeeds,
or entire transaction fails.

Example:

Bank transfer:

Deduct money
Add money

Both must succeed.

Partial success is not allowed.

Interview Answer:

Atomicity guarantees that a transaction is treated as a single indivisible unit.

==================================================
13. ATOMICITY EXAMPLE
==================================================

BEGIN;

UPDATE account
SET balance = balance - 1000
WHERE account_id = 1;

UPDATE account
SET balance = balance + 1000
WHERE account_id = 2;

COMMIT;

If second update fails:

ROLLBACK happens.

No money is lost.

==================================================
14. CONSISTENCY
==================================================

Consistency means:

Database moves from one valid state to another valid state.

Rules must never be violated.

Example:

Account balances cannot become negative.

Total money should remain correct.

Before transaction:

A = 5000
B = 3000

Total = 8000

After transfer:

A = 4000
B = 4000

Total = 8000

Consistency maintained.

Interview Answer:

Consistency ensures that all integrity constraints and business rules remain valid before and after a transaction.

==================================================
15. CONSISTENCY EXAMPLE
==================================================

Constraint:

salary > 0

Bad query:

UPDATE employee
SET salary = -1000;

Database rejects operation.

Consistency is preserved.

==================================================
16. ISOLATION
==================================================

Isolation means:

Concurrent transactions should not interfere with each other.

Example:

Two users updating same account simultaneously.

Each transaction should behave as if it is running alone.

Interview Answer:

Isolation ensures concurrent transactions do not affect each other's intermediate states.

==================================================
17. DURABILITY
==================================================

Durability means:

Once transaction commits,
changes survive system crash.

Example:

COMMIT executed.

Power failure occurs.

After database restart:

Changes still exist.

Interview Answer:

Durability guarantees that committed data is permanently stored even after crashes.

==================================================
18. HOW DURABILITY IS ACHIEVED?
==================================================

Database uses:

- WAL (Write Ahead Logging)
- Redo Logs
- Transaction Logs
- Checkpoints

PostgreSQL uses WAL.

Before data page is written,
log is written first.

This enables recovery after crash.

21. AUTOCOMMIT
==================================================

Most databases use Auto Commit mode.

Every SQL statement becomes its own transaction.

Example:

UPDATE employee
SET salary = 50000
WHERE emp_id = 1;

Database automatically commits.

Interview Answer:

Autocommit automatically commits each SQL statement as an individual transaction.

==================================================
22. AUTOCOMMIT VS MANUAL TRANSACTION
==================================================

Autocommit:

Statement executes
→ Commit automatically

Manual:

BEGIN
→ SQL Statements
→ COMMIT / ROLLBACK

Manual transaction is preferred for business operations involving multiple steps.

29. LONG RUNNING TRANSACTIONS
==================================================

Long transactions can cause:

1. Lock contention
2. Blocking
3. High memory usage
4. WAL growth
5. Vacuum issues

Best Practice:

Keep transactions short.

Interview Answer:

Long-running transactions increase locking and resource usage, reducing database performance.

32. DEADLOCK OVERVIEW
==================================================

Transaction A:

Locks row X
Needs row Y

Transaction B:

Locks row Y
Needs row X

Both wait forever.

Database detects deadlock.

One transaction is killed.

Detailed locking covered in Phase 13.

34. COMMON MISTAKES
==================================================

Mistake 1:

Forgetting COMMIT.

Changes remain uncommitted.

------------------------------------------

Mistake 2:

Keeping transaction open too long.

Causes blocking.

------------------------------------------

Mistake 3:

Using transaction for read-only operations unnecessarily.

------------------------------------------

Mistake 4:

Catching exceptions in Spring without rollback handling.

------------------------------------------

Mistake 5:

Performing network calls inside transaction.

Can increase transaction duration.
