🫧 1. What Is Docker?

Docker is a platform used to build, package, distribute and run applications as isolated containers.

A Java application normally depends on a specific JDK or JRE, configuration, ports, certificates and operating-system libraries. Docker helps package these expectations into a repeatable image.

Why Java developers use it: the same packaged application can run consistently on a developer machine, CI server and deployment platform.

📦 2. Image

This section explains image in a practical Java-container context, including why it matters and how it is used.

Read-only template

An image is used as the base for creating one or more containers.

Layered

Java runtime, dependencies and application files are stored in reusable layers.

Portable

The same image can be shared through a registry and run on different machines.

Versioned

Images are identified using repository names, tags and digests.

Example: an image may contain an Eclipse Temurin Java 21 runtime and a packaged Spring Boot JAR.

🚢 3. Container

A container is a running instance of an image.

Docker creates an isolated process from the image and adds runtime settings such as environment variables, networking, mounts and a writable layer.

Image

The application template.

Container

The running application process.

Writable layer

Temporary changes made by that specific container.

Replaceable

Containers should be recreated from images rather than manually repaired.

📝 4. Dockerfile

A Dockerfile is a plain-text file containing instructions that Docker uses to build an image. 

FROM eclipse-temurin:21-jre

WORKDIR /app

COPY target/orders-api.jar app.jar

EXPOSE 8080

ENTRYPOINT ["java", "-jar", "app.jar"]

FROM

Selects the base image.

WORKDIR

Sets the working directory.

COPY

Copies the JAR into the image.

ENTRYPOINT

Defines how the Java application starts.

The Dockerfile makes image creation repeatable and keeps the runtime definition with the application code.

🌉 5. Host Port, Container Port and Port Publishing

This section explains host port, container port and port publishing in a practical Java-container context, including why it matters and how it is used.

-p 8085:8080
   │      │
   │      └── Container port
   └───────── Host port

Container port

The port inside the container where Spring Boot is listening. In this example, the application listens on port 8080.

Host port

The port exposed on the developer machine. Here, port 8085 is used to access the application.

Port publishing

Docker forwards traffic from the host port to the container port.

Application URL

The service becomes available at http://localhost:8085.

Different host ports may point to the same internal container port. This is useful when running multiple instances locally. 
docker run -d --name orders-1 -p 8081:8080 orders-api:1.0
docker run -d --name orders-2 -p 8082:8080 orders-api:1.0

🏷️ 10. Container Name

A readable container name makes commands and troubleshooting easier.

🎤 14. Interview Questions and Answers

This section explains interview questions and answers in a practical Java-container context, including why it matters and how it is used.

What is the difference between EXPOSE and -p?
EXPOSE documents the port expected by the image. The -p option actually publishes a container port on a host port.
How do you view container logs?
Use docker logs container-name. Add -f to follow the logs continuously, or --tail to limit the number of lines.
How do you enter a running container?
Use docker exec -it container-name sh when the image contains a shell. This starts an additional interactive process inside the running container.
What is detached mode?
Detached mode runs the container in the background. It is enabled with -d. Logs can still be viewed separately using docker logs.
Why might a Spring Boot container exit immediately?
The main Java process may fail because the JAR is missing, the entrypoint is wrong, required configuration is unavailable, the port configuration is invalid, or the application throws an exception during startup. Check the exit state and logs first.
Why use a JRE image for the final Spring Boot application?
The application is already compiled into a JAR, so it normally needs only a Java runtime to execute. A JDK is mainly required during compilation and packaging.
Can multiple containers use container port 8080?
Yes. Each container has its own network namespace. They must use different host ports if both are published on the same Docker host, such as 8081:8080 and 8082:8080.

⚖️ Important Differences

These comparisons are common interview topics because they reveal whether you understand build-time and runtime behaviour.

RUN vs CMD

RUN executes while the image is built. CMD is evaluated when a container starts.

ENTRYPOINT vs CMD

ENTRYPOINT is the main executable; CMD usually supplies default arguments.

COPY vs ADD

Prefer COPY for normal file transfer. Use ADD only when its special behaviour is deliberately required.

Build context

The files sent to the builder. Keep it small to improve speed and reduce accidental exposure.

ENTRYPOINT ["java"]\nCMD ["-jar", "app.jar"]
COPY target/app.jar app.jar

🧹 .dockerignore

A .dockerignore file excludes unnecessary files before the build context is sent to Docker.

.git\n.idea\n.vscode\ntarget/\nbuild/\n*.log\n.env\nREADME.md
Benefit: smaller contexts, faster builds and less risk of copying secrets or local files.

🛤️ Docker Networking

Containers need predictable service discovery. Docker networks provide isolation and name-based communication.

docker network create backend-network\n\ndocker run -d \\\n  --name postgres \\\n  --network backend-network \\\n  -e POSTGRES_PASSWORD=secret \\\n  postgres:17\n\ndocker run -d \\\n  --name orders-api \\\n  --network backend-network \\\n  -e SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/orders \\\n  orders-api:1.0
Important: inside orders-api, localhost means the orders-api container itself. Use hostname postgres to reach PostgreSQL.

User-defined network

Provides container-to-container communication and DNS resolution.

Docker DNS

Resolves container or Compose service names to current container IP addresses.

Container IP

Should not be hard-coded because containers are replaceable.

Published port

Required only when the host or external clients need access.

🪴 Volumes and Storage

Containers are disposable, so important data must live outside the writable container layer.

docker volume create postgres-data\n\ndocker run -d \\\n  --name postgres \\\n  -v postgres-data:/var/lib/postgresql/data \\\n  postgres:17

Named volume

Docker-managed persistent storage; suitable for database data.

Bind mount

Maps a known host path; useful for development files and configuration.

Container layer

Temporary writable storage that disappears when the container is removed.

tmpfs

In-memory temporary storage that is not persisted to disk.

🏡 Docker Compose

Compose turns multiple container commands into one readable application definition.

services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_DB: orders
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: appsecret
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d orders"]
      interval: 10s
      timeout: 5s
      retries: 5

  orders-api:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/orders
      SPRING_DATASOURCE_USERNAME: appuser
      SPRING_DATASOURCE_PASSWORD: appsecret
    depends_on:
      postgres:
        condition: service_healthy

volumes:
  postgres-data:
docker compose up -d\ndocker compose up -d --build\ndocker compose ps\ndocker compose logs -f\ndocker compose stop\ndocker compose down\ndocker compose down -v
Readiness: depends_on controls startup coordination. Health checks improve readiness, but the Java application still needs retry and timeout logic.

🧱 Multi-Stage Maven Build

The builder and runtime stages have different responsibilities. Separating them keeps production images smaller and safer.

# syntax=docker/dockerfile:1
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /workspace

COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 \
    mvn -B dependency:go-offline

COPY src ./src
RUN --mount=type=cache,target=/root/.m2 \
    mvn -B clean package -DskipTests

FROM eclipse-temurin:21-jre
WORKDIR /app

RUN addgroup --system spring \
    && adduser --system --ingroup spring spring

COPY --from=build /workspace/target/*.jar app.jar
USER spring:spring
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

Build tools excluded

Maven and the JDK stay in the builder stage.

Source excluded

Only the packaged JAR is copied to runtime.

Smaller runtime

Fewer tools and files reduce pull size.

Reduced attack surface

The final image contains fewer exploitable components.

🧠 Container-Aware JVM

Modern JVMs understand container limits, but the whole process still needs careful memory planning.

Heap memory

Stores Java objects and is managed by the garbage collector.

Metaspace

Stores class metadata outside the Java heap.

Thread stacks

Each platform thread consumes native stack memory.

Direct buffers

Off-heap buffers used by NIO and networking libraries.

Native memory

Includes JVM internals, GC, libraries and operating-system allocations.

CPU throttling

Strict CPU limits can increase latency and affect GC behaviour.

docker run \\\n  --memory=768m \\\n  --cpus=1.5 \\\n  -e JAVA_TOOL_OPTIONS="\\\n-XX:MaxRAMPercentage=70 \\\n-XX:InitialRAMPercentage=25 \\\n-XX:+ExitOnOutOfMemoryError" \\\n  orders-api:1.0
Do not set Java heap equal to the complete container limit. Leave room for metaspace, stacks, direct memory, code cache and native libraries.

💥 OOMKilled vs Java OutOfMemoryError

These failures look similar but happen at different layers and require different diagnosis.

Java heap OOM

The JVM cannot allocate more objects in the configured heap.

OOMKilled

The operating system kills the process because total container memory exceeds the limit.

Why they differ

A process can exceed total memory because of non-heap or native allocations even when heap still has space.

Diagnosis

Inspect container state, limits, heap settings, threads, direct memory and native usage.

🍃 PID 1 and Signals

The process running as PID 1 controls how termination signals reach the Java application.

ENTRYPOINT ["java", "-jar", "app.jar"]\n\n# Avoid shell form\nENTRYPOINT java -jar app.jar

Exec form makes Java the main process so it receives termination signals directly. This supports Spring Boot graceful shutdown.

🚀 Level 7 - BuildKit, Caching and Image Optimization

Make builds fast and predictable

This level explains how BuildKit decides whether work can be reused and how dependency cache, remote cache and layer ordering speed up both local and CI builds.

  • Cache invalidation
  • BuildKit cache mounts
  • Registry cache and layer inspection

🎯 Goal

Understand cache invalidation, BuildKit cache mounts, registry cache and image inspection.

🪜 Cache Optimization

Dockerfile order determines how much work BuildKit can reuse.

Bad order:
COPY . .\nRUN mvn package
Better order:
COPY pom.xml .\nRUN mvn dependency:go-offline\n\nCOPY src ./src\nRUN mvn package

Dependency metadata changes less often than source code. Copying it first allows the dependency layer to remain reusable.

🧰 BuildKit Cache Mount

Cache mounts speed up dependency-heavy Java builds without polluting the final image.

RUN --mount=type=cache,target=/root/.m2 \\\n    mvn -B clean package

The cache persists Maven downloads for future builds without copying them into the final image layer.

☁️ Registry Cache for CI

Remote cache helps short-lived CI agents reuse work from earlier builds.

docker buildx build \\\n  --cache-from type=registry,ref=registry.example.com/orders-api:buildcache \\\n  --cache-to type=registry,ref=registry.example.com/orders-api:buildcache,mode=max \\\n  -t registry.example.com/orders-api:1.0 \\\n  --push .

This is useful for ephemeral CI agents that do not retain local cache after a build.

🔬 Image Inspection

Inspection tools reveal where image size and build cache are being consumed.

docker history orders-api:1.0\ndocker image inspect orders-api:1.0\ndocker buildx du\ndocker system df

Multi-stage build

Keep build tools outside the runtime image.

Small context

Use .dockerignore and avoid sending unnecessary files.

Minimal packages

Do not install tools that are not required at runtime.

Separate layers

Keep dependencies and application content in different layers.

No build output

Do not copy test reports, source or caches into runtime.

Regular rebuilds

Rebuild images to receive base-image security fixes.

🧤 Runtime Hardening

These flags restrict what a compromised application can change or access.

docker run \\\n  --read-only \\\n  --tmpfs /tmp \\\n  --cap-drop ALL \\\n  --security-opt no-new-privileges \\\n  orders-api:1.0

🔑 Build Secrets

Secrets required during a build should be temporary and must never become part of image history.

ARG DB_PASSWORD\nENV DB_PASSWORD=$DB_PASSWORD
Do not use ARG or ENV to bake credentials into images.
RUN --mount=type=secret,id=maven_settings \\\n    mvn -s /run/secrets/maven_settings package
Use a temporary BuildKit secret mount instead.

⚠️ Docker Socket Risk

The Docker socket is effectively a privileged control interface to the host.

/var/run/docker.sock provides powerful daemon access. A user with socket access may start privileged containers or mount host paths, effectively controlling the host.
